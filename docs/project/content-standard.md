# Стандарт учебного материала

Этот документ задаёт общий редакционный минимум Goracle. Он нужен авторам и
рецензентам, но не требует превращать все главы в одинаковые анкеты.

## Для кого написан проект

Основной читатель — стажёр или младший Go-разработчик, уже умеющий читать простой
код. Углублённые страницы о компиляторе и среде выполнения должны оставаться
необязательными и не прерывать основной учебный маршрут.

## Что должна дать тема

У каждой тематической главы должны быть:

1. предварительные знания и проверяемый результат изучения;
2. минимальная модель, достаточная для типовой задачи начинающего разработчика;
3. пример корректного применения и разбор характерной ошибки;
4. практика с понятным способом самопроверки;
5. краткий итог и осмысленное продолжение;
6. первичные источники для версионных и спорных утверждений.

Раздел добавляется только тогда, когда он помогает конкретной теме. Например,
отдельный словарь внутри главы не нужен, если все термины уже определены в тексте.

## Три уровня материала

- **Обязательный минимум** — договор языка или API и повседневное применение.
- **Практика** — ошибки, диагностика, ограничения и выбор подхода.
- **Углубление** — устройство компилятора, среды выполнения или внешней системы.

Деталь реализации объясняется рядом с местом, где она влияет на вывод. Общая
вводная оговорка о том, что внутренности могут меняться, не заменяет точного
указания версии и источника.

## Примеры кода

Полная программа должна содержать пакет и необходимые импорты. Неполный фрагмент
должен быть понятен из окружающего текста и не выдаваться за самостоятельную
программу. Ключевые примеры связываются с модулем `examples` и проверяются как
обычный Go-код.

Утверждение о производительности требует воспроизводимого теста, профиля либо
явной пометки, что это предположение для последующего измерения. Число без
описания оборудования, входных данных и команды запуска не считается доказательством.

## Язык

- В русском тексте используются русские термины.
- Английский вариант приводится один раз в скобках, если он нужен для поиска
  документации или принят в именах инструментов.
- Имена пакетов, функций, типов, команд, протоколов и параметры настройки не
  переводятся.
- Категоричные слова «всегда» и «никогда» допустимы только для настоящих
  гарантий или запретов; рекомендация должна называть условия применимости.
- Блок «Зачем это Go-разработчику» остаётся только когда из него следует новый
  практический вывод.

Предпочтительные варианты терминов собраны в [словаре](../glossary.md).

## Источники

Приоритет источников:

1. спецификация Go, документация пакета и примечания к выпуску;
2. RFC или документация владельца протокола;
3. исходный код закреплённой версии;
4. официальный технический блог;
5. дополнительная статья с ясно указанным автором.

Ссылка на главную страницу проекта не подтверждает конкретное утверждение.
Ссылка на исходный код должна вести на тег или коммит, если объяснение зависит
от реализации. Существующие изображения сохраняются без изменений: их проверка
и замена не входят в текущую редакцию.

## Обновление на новую версию Go

1. Прочитать примечания к выпуску и список изменений стандартной библиотеки.
2. Найти упоминания прежней версии в главах и примерах.
3. Перепроверить API, диагностику компилятора и сведения о среде выполнения.
4. Обновить примеры, ссылки и метаданные только после успешных тестов.
5. Запустить полный набор проверок и записать результат в аудит.
