# Компиляция и запуск Go-программы

> **Проверено:** Go 1.27 · **Уровень:** младший разработчик — углублённый

[Маршрут раздела «Компиляция и оптимизации»](compilation.md).

## Общая схема

Команда `go build` управляет несколькими инструментами. Упрощённо сборка исполняемой
программы выглядит так:

```text
файлы .go ──→ компилятор ──┐
                            ├──→ объектные данные пакета ──→ компоновщик ──→ программа
файлы .s  ──→ ассемблер ───┘
```

Исходный код Go обычно не превращается в промежуточные файлы `.s`. Компилятор сразу
создаёт объектные данные с машинным кодом, метаданными типов и сведениями об
экспортируемых объявлениях. Флаг `-S` печатает текстовое представление получившихся
инструкций для диагностики, но эта печать не становится обязательной стадией сборки.

Файлы `.s`, которые автор проекта может написать вручную, обрабатываются отдельным
ассемблером Go. Их объектные данные объединяются с результатом компиляции файлов
`.go`. Компоновщик разрешает ссылки между символами пакетов и формирует исполняемый
файл либо другой результат, выбранный через `-buildmode`.

Конкретные временные имена и формат промежуточных файлов — детали набора инструментов.
Команда `go` также вычисляет граф зависимостей и использует кэш сборки, поэтому
неизменившийся пакет обычно не компилируется повторно.

## Что делает каждый инструмент

### Команда `go`

`go build` — управляющая команда, а не сам компилятор. Она:

1. читает модуль, ограничения сборки и список импортов;
2. строит граф пакетов в порядке зависимостей;
3. использует подходящие результаты из кэша;
4. запускает компилятор и при необходимости ассемблер для изменившихся пакетов;
5. запускает компоновщик для пакета `main`.

Флаг `-x` выводит запускаемые команды. Флаг `-work` дополнительно печатает путь к
временной рабочей директории и не удаляет её после сборки:

```bash
go build -x -o app .
go build -work -x -o app .
```

Вывод зависит от операционной системы, архитектуры, кэша и версии Go. По этой причине
не следует запоминать конкретные пути из одного запуска.

### Компилятор

Компилятор обрабатывает исходные файлы `.go` одного пакета. Основные этапы:

1. синтаксический разбор;
2. проверка типов;
3. построение и преобразование внутреннего представления;
4. анализ времени жизни значений и встраивание подходящих функций;
5. построение SSA-представления;
6. генерация машинного кода и метаданных пакета.

Посмотреть решения оптимизатора и листинг инструкций можно так:

```bash
go build -gcflags='-m=2' .
go build -gcflags='-S' .
```

Первая команда помогает исследовать анализ времени жизни и встраивание функций.
Вторая печатает большой низкоуровневый листинг и нужна для точечного разбора, а не
для обычной разработки.

#### Как связаны основные оптимизации

| Механизм | Что меняет | Как исследовать |
|---|---|---|
| Анализ времени жизни | Решает, может ли значение находиться в стеке или должно попасть в кучу | `-gcflags='all=-m=2'`, профиль выделений |
| Встраивание функций | Заменяет подходящий вызов телом функции | `-gcflags='all=-m=2'`, тест производительности |
| Девиртуализация | Заменяет доказанный интерфейсный вызов прямым | `-m=2`, SSA и профиль процессора |
| Свёртка констант и удаление кода | Вычисляет известные выражения и исключает недостижимые участки | SSA или листинг `-S` для узкой функции |
| PGO | Использует профиль для решений о горячих путях, включая встраивание и девиртуализацию | одинаковый тест до и после сборки с `-pgo` |

Механизмы влияют друг на друга. После девиртуализации вызов может стать кандидатом
на встраивание, а после встраивания анализ времени жизни получает больше сведений и
иногда устраняет выделение в куче. Это возможность конкретной сборки, а не гарантия
для всякой функции.

Практический маршрут и границы этих инструментов собраны на странице
[«Компиляция и оптимизации Go»](compilation.md). Подробности рассматриваются в
главах об [анализе времени жизни](Анализ%20времени%20жизни/escape-analysis.md)
и [встраивании функций](Встраивание%20функций/inlining.md).

### Ассемблер

Ассемблер Go обрабатывает файлы `.s`, написанные в синтаксисе ассемблера Go. Такой
код используется в среде выполнения, криптографических реализациях и других местах,
где нужны платформенные инструкции или особое управление регистрами.

Ассемблер не является обязательной промежуточной стадией для каждого файла `.go`.
Это параллельный путь для исходных файлов другого типа.

### Компоновщик

Компоновщик получает объектные данные пакета `main` и его зависимостей, разрешает
ссылки между символами, размещает код и данные в секциях итогового файла и добавляет
точку входа для выбранной платформы.

Обычная программа Go часто не требует внешнего системного компоновщика. Но cgo,
некоторые режимы сборки и платформенные условия могут включить внешнюю компоновку и
динамические библиотеки. Поэтому утверждение «любой исполняемый файл Go полностью
статический» неверно.

Список символов готовой программы можно исследовать командой:

```bash
go tool nm app
```

После сборки с удалением таблицы символов часть сведений для `nm` будет недоступна.

## Как компилятор связывает язык со средой выполнения

Компилятор не выполняет простую текстовую замену всех ключевых слов на функции
пакета `runtime`. Он преобразует программу во внутреннее представление и для
конкретных операций либо генерирует инструкции непосредственно, либо вставляет
обращение к среде выполнения.

### Запуск горутины

Для оператора:

```go
go f(x)
```

компилятор подготавливает функцию-обёртку и данные вызова, а затем создаёт обращение к
`runtime.newproc`. Это реализация семантики оператора `go`, но не доступный
разработчику договор: внутреннее имя и форма вызова могут меняться между версиями.

### Выделение памяти

Вызов `new(T)` не означает безусловный вызов `runtime.newobject`. После анализа
времени жизни компилятор может:

* разместить значение в стеке текущей горутины;
* полностью устранить выделение после оптимизации;
* вызвать функцию среды выполнения, если объект должен находиться в куче.

Поэтому наличие `new` в исходном коде само по себе не доказывает выделение памяти в
куче. Решение проверяют через `-gcflags='-m=2'` и измерения.

### Встроенные операции и ассемблерные функции

Некоторые внутренние функции распознаются компилятором специально. Например,
`runtime.getg` преобразуется в операцию получения указателя на текущую G без
обычного вызова Go-функции. Другие операции зависят от архитектуры: переключение
контекста через `gogo` реализовано в ассемблерных файлах среды выполнения.

Именно поэтому исходный код пакета `runtime` состоит из Go и ассемблера, но это не
означает, что весь пользовательский Go-код сначала переводится в текстовый ассемблер.

## Как среда выполнения попадает в программу

Пакет `runtime` является частью каждой обычной Go-программы. Компоновщик включает
необходимый код планировщика, управления памятью, сборщика мусора, обработки паник и
платформенного запуска в итоговый файл.

Среда выполнения — не отдельная виртуальная машина и не фоновая программа рядом с
приложением. Её функции выполняются внутри того же процесса и тех же потоков ОС, что
и пользовательский код.

### `//go:linkname`

Директива `//go:linkname` связывает локальное объявление с объектным символом,
который может принадлежать другому пакету. Например, в Go 1.27 реализация
`runtime.timeSleep` связана с публичной функцией `time.Sleep`.

Эта директива обходится без обычной проверки доступности идентификатора между
пакетами и предназначена прежде всего для самого набора инструментов и среды
выполнения. Использовать её как обычный способ доступа к внутренностям чужого пакета
опасно: внутренний символ не обязан сохранять имя, сигнатуру и поведение.

## Что происходит при запуске

После сборки путь до пользовательской `main` выглядит так:

1. Загрузчик ОС отображает исполняемый файл и библиотеки в память процесса.
2. Управление передаётся платформенной точке входа программы.
3. Код среды выполнения подготавливает основной поток M0, его системную горутину g0
   и доступ к текущей G.
4. `runtime.schedinit` инициализирует планировщик, память, сборщик мусора и набор P.
5. Создаётся горутина для `runtime.main`, после чего M0 входит в цикл планирования.
6. `runtime.main` запускает необходимые служебные компоненты, выполняет функции
   `init`, а затем вызывает пользовательскую `main.main`.
7. Возврат из `main.main` завершает программу; среда выполнения не ждёт остальные
   пользовательские горутины автоматически.

Низкоуровневая точка входа зависит от операционной системы и архитектуры. На многих
поддерживаемых архитектурах основной путь проходит через ассемблерную функцию
`runtime.rt0_go`. Подробное устройство G, M, P и дальнейшего цикла описано в
[справочнике по планировщику](../Планировщик%20Go/reference.md).

## Частые заблуждения

| Заблуждение | Корректная модель |
|---|---|
| каждый `.go` сначала превращается в `.s` | компилятор создаёт объектные данные напрямую; `.s` собираются отдельным путём |
| `go build` — это компилятор | команда `go` управляет компилятором, ассемблером, компоновщиком и кэшем |
| `new` всегда вызывает `runtime.newobject` | размещение зависит от анализа времени жизни и оптимизаций |
| среда выполнения — отдельный процесс | её код входит в программу и выполняется внутри процесса приложения |
| любой файл Go полностью статический | результат зависит от cgo, режима компоновки и платформы |
| `//go:linkname` — безопасный публичный API | директива обходит границы пакетов и связывает код с нестабильными внутренностями |

## Практика

Создайте небольшую программу:

```go
package main

import "fmt"

func main() {
    value := new(int)
    *value = 42
    fmt.Println(*value)
}
```

Выполните:

```bash
go build -work -x -o app .
go build -gcflags='-m=2' -o app .
go tool nm app
```

Проверьте себя:

1. Найдите в выводе `-x` запуск компилятора и компоновщика.
2. Убедитесь, что между ними нет обязательного создания `.s` из вашего `.go`.
3. По выводу `-m=2` определите, понадобилось ли `value` выделение в куче.
4. Найдите через `go tool nm app` символы `runtime.main` и `main.main`.

## Краткий итог

* Файлы `.go` компилируются в объектные данные, а исходные `.s` обрабатываются
  отдельным ассемблером.
* `go build` строит граф пакетов, использует кэш и управляет инструментами сборки.
* Компилятор реализует часть операций напрямую, а для части обращается к `runtime`.
* Среда выполнения включается в программу и начинает работу до пользовательской
  `main`.
