# Встраивание функций: практическое руководство

> **Проверено:** Go 1.27
>
> **Перед чтением:** [компиляция и запуск](../compilation-and-startup.md), вызовы функций, профилирование и тесты производительности.
>
> **После чтения:** вы сможете прочитать решение компилятора и измерить влияние встраивания.
>
> **Практика:** [задания и самопроверка](../../../practice.md#inlining).

## Что делает встраивание

Встраивание заменяет вызов телом функции и открывает дополнительные оптимизации,
включая анализ времени жизни и девиртуализацию. Оно может ускорить горячий путь, но
увеличить двоичный файл и нагрузку на кэш инструкций.

Исходный код:

```go
func add(left, right int) int {
	return left + right
}

result := add(2, 3)
```

После встраивания машинный код может соответствовать следующей упрощённой модели:

```go
result := 2 + 3
```

Компилятор не переписывает файл на диске. Он преобразует внутреннее представление
конкретного места вызова. После подстановки ему могут стать доступны свёртка
константы, удаление лишнего кода и более точный анализ времени жизни значений.

Стоимость вызова небольшой функции обычно невелика, поэтому само исчезновение
инструкции вызова ещё не доказывает заметное ускорение. Выигрыш часто появляется из
последующих оптимизаций. Обратная сторона — копирование тела функции в несколько
мест, рост машинного кода и возможное ухудшение локальности кэша инструкций.

## Как узнать решение компилятора

Соберите исследуемый пакет с подробной диагностикой:

```bash
go build -gcflags='all=-m=2' ./...
```

В выводе различайте два сообщения:

- `can inline add` — тело функции допускает встраивание;
- `inlining call to add` — компилятор действительно встроил конкретный вызов.

Первое сообщение не гарантирует второе для каждого места вызова. Решение зависит от
контекста, бюджета роста кода, доступных сведений о типах и профиля PGO. Причина
отказа вроде `function too complex` относится к этой версии компилятора и не
является рекомендацией немедленно упрощать функцию.

Флаг `all=` передаёт параметр всем собираемым пакетам и способен создать очень
большой вывод. Для локального исследования сузьте команду до нужного пакета и
фильтруйте сообщение по имени функции или файлу.

## Как проверить влияние

Сначала сохраните обычный результат:

```bash
go test -run '^$' -bench BenchmarkLookup -benchmem -count=10 ./path/to/package
```

Затем сформулируйте гипотезу и измените только одну причину. Сборка с отключённым
встраиванием может служить грубым контрольным вариантом:

```bash
go test -run '^$' -bench BenchmarkLookup -benchmem -count=10 \
  -gcflags='all=-l' ./path/to/package
```

Такое сравнение не изолирует стоимость одного вызова: без встраивания меняются
анализ времени жизни, девиртуализация и последующие проходы. Фиксируйте версию Go,
архитектуру, команды, число выделений и разброс результатов. Для решения о рабочем
коде используйте обычную оптимизированную сборку и представительную нагрузку.

Размер программы тоже является частью компромисса:

```bash
go build -o app ./cmd/app
go tool nm -size app
```

Сравнивать только общий размер файла недостаточно, если на него одновременно влияют
отладочные сведения, зависимости и режим компоновки. Нужен один и тот же проект с
одинаковыми параметрами сборки.

## Связь с другими решениями компилятора

### Анализ времени жизни

После встраивания компилятор видит использование локального значения в вызывающей
функции. Иногда это позволяет доказать, что значение не переживает её кадр, и
устранить выделение в куче. Обратное тоже возможно: изменение графа вызовов меняет
результат анализа, поэтому сопоставляйте сообщения о встраивании и размещении с
`-benchmem` и профилем выделений.

Подробнее: [анализ времени жизни](../Анализ%20времени%20жизни/escape-analysis.md).

### Девиртуализация и PGO

> **Примечание автора:** **девиртуализация** — это замена косвенного вызова через
> интерфейс конкретным прямым вызовом. Обычно нужный метод выбирается во время
> выполнения по динамическому типу значения. Если компилятор смог определить этот
> тип заранее, он может вызвать конкретную функцию напрямую, а затем попытаться
> встроить её.
>
> **PGO** (Profile-Guided Optimization, оптимизация с учётом профиля) — использование
> компилятором профиля процессора, полученного на представительной нагрузке.

Вызов через интерфейс нельзя встроить, пока компилятор не знает конкретную функцию.
Если тип доказан, девиртуализация заменяет интерфейсный вызов прямым, после чего он
может стать кандидатом на встраивание. Профиль PGO помогает компилятору отличать
частые рёбра графа вызовов и выбирать для них больший бюджет роста кода.

PGO не превращает встраивание в гарантию. Проверяйте диагностический вывод и
измеряйте одну и ту же нагрузку до и после сборки с профилем.

## Стеки вызовов и отладка

Физический кадр встроенной функции может отсутствовать, но среда выполнения хранит
сведения, позволяющие восстановить логические кадры. Для программного обхода
используйте `runtime.Callers` вместе с `runtime.CallersFrames`, а не преобразуйте
каждый программный счётчик отдельно через `runtime.FuncForPC`.

Не запрещайте встраивание во всей рабочей программе только ради более привычного
стека. Сначала проверьте возможности отладчика и стандартных средств обработки
стеков; `//go:noinline` оставляйте для узкого эксперимента или подтверждённого
требования.

## Частые ошибки

- **Считать маленькую функцию гарантированно встроенной.** Решение принимается для
  конкретного места вызова и конкретной сборки.
- **Дробить код ради внутреннего бюджета.** Границы ответственности и читаемость
  важнее попытки угадать текущую эвристику.
- **Считать `-l` точным измерением цены вызова.** Флаг отключает и возможности для
  других оптимизаций.
- **Оценивать эффект по одному запуску.** Нужны повторы, одинаковое окружение и
  статистическое сравнение.
- **Запрещать встраивание ради профиля.** Современные средства умеют учитывать
  логические кадры встроенных вызовов.

Устройство эвристик и привязанные к версии исходники разобраны в
[приложении о компиляторе Go 1.27](compiler-reference.md).

## Краткий итог

- Встраивание устраняет часть стоимости вызова и открывает путь другим оптимизациям.
- Решение зависит от текущей сборки, профиля и бюджета компилятора.
- Отключение всего встраивания служит грубым сравнением, но не изолирует одну причину.
- Пользу изменения подтверждают измерением, а не сообщением компилятора.
