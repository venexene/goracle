# Встраивание функций: устройство компилятора Go 1.27

> **Проверено:** Go 1.27 · **Уровень:** младший разработчик — углублённый

**Перед чтением:** [практическое руководство](inlining.md) и
[маршрут «Компиляция и оптимизации»](../compilation.md).
**После главы:** вы сможете связать сообщения `-m=2` с бюджетом компилятора,
встраиванием по цепочке, PGO и последующими оптимизациями.

## 1. Что такое встраивание функций

**Встраивание функций (inlining)** — оптимизация компилятора, при которой конкретный
вызов заменяется представлением тела вызываемой функции.

Проще говоря, компилятор «копирует» код из вызываемой функции и «вставляет» его на место вызова, вместо того чтобы генерировать инструкции для перехода к другой части кода.

```go
func main() {
    result := add(2, 3)
    println(result)
}

func add(a, b int) int {
    return a + b
}

```

Здесь при выполнении `main` происходит вызов `add`: процессор перепрыгивает в код функции `add`, выполняет сложение и возвращается назад.

```go
func main() {
    // Вызов функции add заменён её телом.
    result := 2 + 3
    println(result)
}

func add(a, b int) int {
    return a + b
}

```

### Зачем это нужно?

* **Устранение накладных расходов:** прямой вызов, возврат и часть работы с
  аргументами или кадром могут исчезнуть. Стоимость нельзя задавать «десятками
  наносекунд» без процессора, версии и теста.
* **Открытие возможностей для других оптимизаций:** когда код находится «в одном
  месте», компилятор может применить постоянное свёртывание, удаление мёртвого кода
  и более точный анализ потоков данных.
* **Компромисс размера кода:** исчезновение вызова может помочь часто
  выполняемому пути, но дублирование тела увеличивает двоичный файл и иногда
  ухудшает локальность кэша инструкций. Поэтому компилятор учитывает размер и профиль.

> **Зачем это Go-разработчику.** Встраивание позволяет сохранять небольшие
> осмысленные функции без ручного копирования их тел. Но решение компилятора и его
> влияние на горячий путь нужно проверять, а не выводить только из размера функции.

### Ограничения

* Чем выше оценённая стоимость тела и рост вызывающей функции, тем меньше
  вероятность встраивания. Сам по себе цикл не является безусловным запретом:
  решение зависит от всего тела и места вызова.
* **Непосредственно рекурсивный вызов** не разворачивается бесконечно. Компилятор
  также отслеживает повторяющиеся рекурсивные циклы в текущей цепочке встраивания.
* **Вызов метода через интерфейс** сначала требует доказать конкретную цель. После
  девиртуализации прямой вызов может стать кандидатом на встраивание.
* **Функция с `defer`** в Go 1.27 не допускается текущим алгоритмом встраивания. Это
  ограничение реализации, а не запрет языка.
* Решение принимает компилятор. Директива `//go:noinline` запрещает оптимизацию;
  открытой директивы `//go:inline` в Go нет.

## 2. Когда компилятор выполняет встраивание

Компилятор не может встраивать всё подряд. Он оценивает, допустимо ли тело функции и
не приведёт ли подстановка к чрезмерному росту кода. В диагностике эта оценка
называется **стоимостью (cost)**.

### Что такое «вес» функции?

Это численное значение сложности функции с точки зрения текущего алгоритма. Чем
выше стоимость, тем труднее уложить функцию в доступный бюджет встраивания.

### Как считается стоимость

Компилятор оценивает внутреннее представление функции, место вызова, ожидаемый
выигрыш и рост кода. Конкретные веса меняются между выпусками и не являются
открытым API. Таблица с фиксированной ценой `if`, `for` или вызова быстро
устаревает и не должна определять стиль.

Разделяйте функции по ответственности и читаемости. Если профиль указывает на
частый вызов, смотрите фактическое решение через `-m=2`; не переписывайте код
под предполагаемый счётчик синтаксического дерева.

### Порог встраивания

У компилятора есть внутренние пределы, но одного устойчивого порога «80» для
всех мест вызова нет. Эвристики учитывают контекст и PGO; проверяйте их на своей
версии Go.

## 3. Как узнать, что компилятор встроил функцию

Основной инструмент — флаг `-gcflags="-m"`, который включает вывод решений компилятора об оптимизациях:

```shellscript
go build -gcflags="-m" ./...

```

Вывод покажет:

```

./main.go:12:6: can inline add
./main.go:8:6: can inline main
./main.go:9:5: inlining call to add

```

* `can inline add` — тело `add` допускает встраивание.
* `inlining call to add` — конкретный вызов `add` действительно встроен.
* `function too complex for inlining` — функция не уложилась в условия текущего алгоритма.

Для более подробного вывода используйте `-gcflags="all=-m=2"`.

Глубокий анализ через SSA-дамп

Для просмотра SSA конкретной функции компилятор умеет создавать HTML-отчёт:

```shellscript
GOSSAFUNC=main go build

```

Будет создан `ssa.html`, в котором видны преобразования SSA для выбранной функции.

> **Зачем это Go-разработчику.** При исследовании измеренного узкого места
> проверяйте фактическое решение через `-gcflags='all=-m=2'`. Размер исходного кода
> сам по себе не показывает, будет ли встроен конкретный вызов.

## 4. Управление встраиванием: директивы компилятора

Для пользовательского кода есть директива, запрещающая встраивание. Директивы,
заставляющей компилятор встроить функцию, нет.

### `//go:noinline` — запрет встраивания

Директива запрещает компилятору встраивать функцию. Она ставится непосредственно
перед объявлением:

```go
//go:noinline
func expensiveDebug(x int) int {
    return x * 2
}

```

Применяйте её редко: в тестах компилятора или среды выполнения, в эксперименте,
где измеряется именно граница вызова, либо как подтверждённый обход ошибки.
Обычный тест производительности должен измерять оптимизированный рабочий код;
`//go:noinline` способен сделать результат менее реалистичным.

### Директивы `//go:inline` не существует

Комментарий `//go:inline` не является директивой компилятора и ничего не
рекомендует оптимизатору. Используйте ясный код, PGO и проверку диагностики.

## 5. Встраивание по цепочке вызовов (Go 1.12+)

До Go 1.12 компилятор встраивал только **листовые функции (leaf functions)** — те,
которые сами не вызывают других функций. Это ограничивало применимость оптимизации.

Начиная с Go 1.12, поддерживается **встраивание в середине цепочки вызовов
(mid-stack inlining)**.

### Как это работает

Рассмотрим цепочку: `A → B → C → D`, где `D` — листовая функция.

* **До Go 1.12:** в примере допускается только встраивание листовой `D`.
* **Начиная с Go 1.12:** `D` встраивается в `C`, затем обновлённая `C` может быть
  встроена в `B` и так далее, если каждое место проходит отдельную проверку.

### Предел встраивания по цепочке

Допустимость каждого места вызова зависит от текущего предела и контекста.
Сравнение «~200 против ~80» не является контрактом и быстро устаревает вместе с
оптимизатором и эвристиками PGO.

> **Зачем это Go-разработчику.** Встраивание по цепочке позволяет сохранять
> небольшие вспомогательные функции без ручного разворачивания, но ничего не
> гарантирует для конкретного вызова. Проверяйте диагностику оптимизированной
> сборки и тест производительности.

## 6. Связь с анализом времени жизни и другими оптимизациями

Встраивание не существует изолированно: оно меняет сведения, доступные следующим
проходам компилятора.

### Анализ времени жизни

**Анализ времени жизни (escape analysis)** определяет, может ли значение находиться
в стеке или должно быть размещено в куче. Встраивание может изменить доступный
компилятору контекст и итог анализа.

Рассмотрим пример:

```go
func newInt() *int {
    x := 42
    return &x // x «убегает» в кучу
}

func main() {
    p := newInt()
    fmt.Println(*p)
}

```

Без встраивания `x` может попасть в кучу, потому что ссылка покидает `newInt`. Если
вызов `newInt` встроен в `main`, компилятор видит дальнейшее использование и иногда
может доказать, что отдельное выделение в куче не требуется. Проверяйте фактический
результат через `-m=2` и `-benchmem`.

### Девиртуализация

**Девиртуализация (devirtualization)** — это замена вызова метода через интерфейс прямым вызовом конкретного типа. Если компилятор может доказать, какой конкретный тип скрывается за интерфейсом, он:

1. Заменяет интерфейсный вызов прямым.
2. После этого прямой вызов может быть встроен.

```go
var w io.Writer = os.Stdout
w.Write([]byte("hello")) // интерфейсный вызов

```

Если компилятор докажет, что `w` имеет конкретный тип `*os.File`, вызов `Write`
может быть девиртуализован, а затем встроен.

### Распространение и свёртка констант

После встраивания компилятор видит фактические значения аргументов и может:

* вычислить выражение на этапе компиляции;
* удалить ветки, недостижимые при известных значениях аргументов.

> **Зачем это Go-разработчику.** Польза встраивания может заключаться не столько в
> удалении вызова, сколько в возможности устранить выделение, вычислить константу
> или удалить недостижимый код.

## 7. PGO: оптимизация с учётом профиля

**PGO (Profile-Guided Optimization)** — оптимизация, при которой компилятор
использует профиль процессора от предыдущего запуска программы. Обычная компиляция
оценивает важность вызовов только по структуре исходного кода и внутренним
эвристикам. Профиль добавляет сведения о том, какие функции и переходы между ними
действительно были горячими на измеренной нагрузке.

```text
представительная нагрузка
          ↓
   профиль процессора
          ↓
исходный код + профиль ──→ компилятор ──→ двоичный файл с PGO
                                                ↓
                                    повторное измерение результата
```

### Как профиль влияет на встраивание

Профиль содержит образцы стеков вызовов и их частоту. Компилятор сопоставляет их с
рёбрами графа вызовов и может предоставить больший бюджет роста кода часто
выполняемым местам. Это позволяет встроить горячий вызов, который без профиля не
прошёл бы обычную оценку стоимости. Холодные вызовы при этом не получают такого
приоритета.

PGO также помогает **девиртуализации** интерфейсных вызовов. Если профиль показывает,
что в горячем месте почти всегда встречается один конкретный тип, компилятор может
создать быстрый путь:

```text
динамический тип совпал с ожидаемым?
        ├── да  → прямой вызов → возможное встраивание
        └── нет → исходный косвенный вызов через интерфейс
```

Проверка типа и запасной путь сохраняют правильное поведение программы, если во
время нового запуска встретится другой тип.

### Как передать профиль сборке

Для PGO нужен профиль процессора в формате `pprof`, полученный на нагрузке, похожей
на рабочую. Его можно собрать средствами `runtime/pprof`, `net/http/pprof` или во
время представительного теста производительности:

```bash
go test -run '^$' -bench BenchmarkServe -cpuprofile=cpu.pprof ./internal/service
go build -pgo=cpu.pprof ./cmd/service
```

По умолчанию команда `go build` использует режим `-pgo=auto`. Для каждого главного
пакета она ищет файл `default.pgo` в его каталоге и, если находит, применяет профиль
к главному пакету и его транзитивным зависимостям. Режим можно указать явно:

```bash
go build -pgo=default.pgo ./cmd/service # применить выбранный профиль
go build -pgo=off ./cmd/service         # собрать без PGO для сравнения
```

### Ограничения и проверка результата

- Профиль отражает только выполненную нагрузку. Непредставительный профиль может
  направить бюджет оптимизации на второстепенные пути.
- PGO не меняет договор языка и не гарантирует встраивание конкретного вызова.
- Профиль процессора сообщает частоту выполнения, а не причину задержки и не данные
  профиля памяти.
- Изменение исходного кода или версии компилятора может изменить сопоставление
  профиля и решения оптимизатора.
- Ускорение одного пути иногда оплачивается большим машинным кодом, временем сборки
  или поведением кэша инструкций.

Проверяйте решение компилятора и измеряйте одинаковую нагрузку с профилем и без него:

```bash
go build -pgo=cpu.pprof -gcflags='all=-m=2' ./cmd/service
go test -run '^$' -bench BenchmarkServe -benchmem -count=10 -pgo=off ./internal/service
go test -run '^$' -bench BenchmarkServe -benchmem -count=10 -pgo=cpu.pprof ./internal/service
```

Сохраняйте вместе профиль, версию Go, параметры сборки и описание нагрузки. Иначе
результат трудно воспроизвести, а изменение показателей нельзя уверенно связать с
PGO.

> **Зачем это Go-разработчику.** PGO позволяет оптимизировать действительно горячие
> пути без ручного разворачивания функций и предположений о частоте вызовов. Пользу
> подтверждайте сравнением одинаковой нагрузки с профилем и без него.

## 8. Влияние на отладку и стеки вызовов

Компилятор записывает сведения о встроенных функциях. Современные стеки вызовов,
`runtime.CallersFrames` и pprof умеют раскрывать логические кадры, поэтому
функция не обязана исчезать из диагностики.

### Как встраивание меняет стек вызовов

Рассмотрим цепочку `main → process → validate`, где вызов `validate` встроен в
`process`:

**Стек без встраивания:**

```

goroutine 1 [running]:
main.validate(...)
    /app/main.go:25
main.process(...)
    /app/main.go:15
main.main()
    /app/main.go:8

```

**Стек со встроенным вызовом `validate`:**

```

goroutine 1 [running]:
main.process(...)
    /app/main.go:15
main.main()
    /app/main.go:8

```

Показанный сокращённый стек не является общим поведением современного Go:
обычная трассировка паники способна показать `validate(...)` как встроенный кадр
и правильную строку исходного кода. Обход адресов команд должен использовать
`runtime.CallersFrames`, который корректно разворачивает эти сведения.

### Что показывает pprof

`go tool pprof` использует символы и сведения о встраивании для отнесения
образцов. При расхождениях проверяйте соответствие профиля двоичному файлу и
наличие отладочной информации, а не отключайте оптимизацию заранее.

### Практические рекомендации по отладке

* Для получения кадров из адресов команд используйте `runtime.CallersFrames`.
* Не ставьте `//go:noinline` на пути проверки и ошибок только ради трассировок.
* Используйте `GOTRACEBACK=system`, когда при диагностике нужны кадры среды выполнения.

> **Зачем это Go-разработчику.** Используйте инструменты, понимающие сведения о
> встраивании. Отключайте оптимизацию только для узкого эксперимента, а не как
> постоянную политику наблюдаемости.

## 10. Проверяемый эксперимент

Встраивание оценивайте вместе со скоростью, размером двоичного файла и выделениями:

```bash
go test -run '^$' -bench BenchmarkLookup -benchmem -count=10
go test -c -o app.test
go build -gcflags='all=-m=2' ./cmd/app
```

Сравнивайте результаты статистическим инструментом, а не одной парой чисел.
Отдельная сборка с `-gcflags='all=-l'` полезна как контроль без встраивания, но она
меняет и последующие оптимизации, поэтому не изолирует стоимость одного вызова.

PGO может повысить бюджет встраивания для горячих рёбер графа вызовов и помочь
девиртуализации. Храните профиль, версию Go и исходную нагрузку вместе с результатом:
смена компилятора способна изменить решение без правки исходного кода.

Для корректного обхода кадров стека используйте `runtime.Callers` вместе с
`runtime.CallersFrames`: эта пара учитывает встроенные вызовы лучше, чем ручное
преобразование каждого программного счётчика через `runtime.FuncForPC`.
