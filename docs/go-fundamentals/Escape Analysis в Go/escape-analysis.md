# Анализ времени жизни: практическое руководство

> **Проверено:** Go 1.27 · **Уровень:** младший разработчик — углублённый
> Исходный код и нестабильные детали компилятора вынесены в приложение.

**Перед чтением:** указатели, стек, куча и тесты производительности. **После главы:**
вы сможете проверить гипотезу о выделении через профиль, `-m=2` и повторный замер,
не делая вывод по одному синтаксическому признаку. [Задания и самопроверка](../../practice.md#escape-analysis).

Компилятор решает, может ли значение жить в стеке или должно пережить текущий кадр.
Указатель сам по себе не означает кучу, а возврат значения не гарантирует стек.
Решение зависит от всего пути ссылок, встраивания и возможностей конкретной версии.

Рабочий процесс:

```bash
go test -run '^$' -bench . -benchmem -count=10
go build -gcflags='all=-m=2' ./...
go test -memprofile=mem.pprof ./...
go tool pprof mem.pprof
```

Сначала подтвердите цену профилем, затем найдите объяснение компилятора, измените одну
причину и повторите замер. PGO и девиртуализация могут изменить результат. Сообщение
`moved to heap` — диагноз размещения, а не требование немедленно переписать код.

Подробнее: [алгоритм и исходный код компилятора Go 1.27](compiler-reference.md).

**Основные источники:** документация команды [`go build`](https://pkg.go.dev/cmd/go#hdr-Compile_packages_and_dependencies) и [справочник по компилятору Go 1.27](compiler-reference.md).

## Краткий итог

- Компилятор выбирает размещение по доказанному времени жизни значения.
- Сообщение `moved to heap` объясняет решение сборки, но само по себе не доказывает проблему.
- Влияние изменения проверяют тестом производительности и профилем выделений.

Дальше: сопоставьте выделения с [живой кучей и работой сборщика](../Память%20в%20Go/memory.md).
