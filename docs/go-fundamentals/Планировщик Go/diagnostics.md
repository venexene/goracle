# Диагностика и настройка планировщика

> **Проверено:** Go 1.27
>
> **Перед чтением:** [модель GMP](gmp.md), контекст и основы профилирования.
>
> **После чтения:** вы сможете выбрать источник данных по симптому, записать профиль или трассировку и проверить гипотезу.
>
> **Практика:** [задания и самопроверка](../../practice.md#scheduler).

Проблему не следует сразу приписывать планировщику. Долгий ответ может быть вызван
медленной базой данных, блокировкой, сборкой мусора, исчерпанием пула соединений или
очередью приложения. Планировщик становится предметом исследования, когда нужно
понять, почему готовая к работе горутина долго не получает процессор либо где и в
каком порядке горутины блокируются.

## С чего начинать

Сначала зафиксируйте условия, при которых проявился симптом:

1. время и длительность события;
2. версию Go, `GOOS`, `GOARCH` и значение `GOMAXPROCS`;
3. нагрузку: число запросов, размер очереди и ограничения конкурентности;
4. загрузку процессора, число горутин и хвостовые задержки;
5. изменения конфигурации и версии приложения.

Один снимок почти ничего не доказывает. Сравнивайте исправную и проблемную работу
при сопоставимой нагрузке, а накопительные показатели рассматривайте как изменение
за интервал.

## Как выбрать инструмент

| Симптом | Первый источник данных | Что проверять дальше |
|---|---|---|
| процессор постоянно занят | профиль процессора | горячий прикладной код, сборщик, синхронизация |
| запросы задерживаются при свободном процессоре | профиль блокировок и горутин | внешние операции, каналы, очереди, потерянная отмена |
| растёт время ожидания мьютекса | профиль мьютексов | длительность критической секции и общий владелец состояния |
| растёт число горутин | профиль горутин в разные моменты | повторяющиеся стеки, незавершённые отправки и внешние вызовы |
| горутины долго готовы, но не выполняются | `/sched/latencies:seconds` | число готовых горутин, загрузка процессора и трассировка |
| важен порядок короткого редкого события | трассировка или `FlightRecorder` | переходы состояний конкретных горутин |

Профиль агрегирует стоимость за интервал. Трассировка сохраняет порядок событий,
поэтому она полезнее для вопроса «что произошло сначала», но обычно создаёт больше
данных и требует короткого окна записи.

## Метрики среды выполнения

Пакет `runtime/metrics` предоставляет несколько показателей планировщика:

| Метрика | Значение |
|---|---|
| `/sched/gomaxprocs:threads` | сколько P может одновременно выполнять Go-код |
| `/sched/goroutines:goroutines` | текущее число живых горутин |
| `/sched/goroutines/runnable:goroutines` | примерное число готовых, но ещё не выполняющихся горутин |
| `/sched/goroutines/running:goroutines` | примерное число выполняющихся горутин |
| `/sched/goroutines/waiting:goroutines` | примерное число горутин, ожидающих ресурс или ввод-вывод |
| `/sched/threads/total:threads` | число живых потоков ОС, принадлежащих среде выполнения |
| `/sched/latencies:seconds` | распределение времени между готовностью горутины и началом выполнения |

Число ожидающих горутин само по себе не является ошибкой: у незагруженного сервера
большинство горутин законно ждёт сеть, канал или таймер. Ищите рост относительно
обычного уровня и одинаковые стеки ожидания. Приближённые показатели состояний не
обязаны в сумме совпадать с общим числом горутин.

`/sched/latencies:seconds` — накопительная гистограмма. Для панели наблюдения нужны
изменения счётчиков между измерениями и квантили за выбранное окно, а не сумма за всё
время жизни процесса. Рост задержки планирования нужно сопоставлять с загрузкой
процессора, готовыми горутинами и паузами сборщика мусора.

## Профили `pprof`

Для службы можно подключить `net/http/pprof` к отдельному внутреннему адресу. Не
публикуйте диагностические обработчики в открытом интернете: профили раскрывают
структуру программы и могут создавать заметную нагрузку.

Пример записи тридцатисекундного профиля процессора:

```bash
curl -o cpu.pprof 'http://127.0.0.1:6060/debug/pprof/profile?seconds=30'
go tool pprof -http=:0 cpu.pprof
```

Снимок горутин лучше сохранять в двоичном формате, чтобы открыть его через `pprof`:

```bash
curl -o goroutine.pprof 'http://127.0.0.1:6060/debug/pprof/goroutine?debug=0'
go tool pprof -http=:0 goroutine.pprof
```

Профиль процессора не показывает время ожидания. Для него используйте профили
блокировок и мьютексов. Их частоту выборки повышают только на время исследования:
агрессивный сбор способен изменить поведение самой программы.

Профиль блокировок по умолчанию не собирает события. На время ограниченного
исследования приложение может включить выборку:

```go
runtime.SetBlockProfileRate(1)       // записывать каждое событие блокировки
runtime.SetMutexProfileFraction(1)   // записывать каждое событие конкуренции за мьютекс
```

Значение `1` даёт наиболее подробные данные и может быть слишком дорогим для
рабочей нагрузки. Подберите меньшую частоту экспериментально и после исследования
верните `0`. Если подключён `net/http/pprof`, результаты сохраняются так:

```bash
curl -o block.pprof 'http://127.0.0.1:6060/debug/pprof/block'
go tool pprof -http=:0 block.pprof

curl -o mutex.pprof 'http://127.0.0.1:6060/debug/pprof/mutex'
go tool pprof -http=:0 mutex.pprof
```

Профиль блокировок показывает места, где завершилось ожидание синхронизации, а
профиль мьютексов — стеки владельцев, задержавших другие горутины. Они не заменяют
профиль горутин: навсегда ожидающая G ещё не создала завершённого события, которое
можно было бы агрегировать.

## Короткая трассировка

Если служба предоставляет внутренний обработчик `pprof`, запишите несколько секунд
выполнения и откройте результат стандартным инструментом:

```bash
curl -o trace.out 'http://127.0.0.1:6060/debug/pprof/trace?seconds=5'
go tool trace trace.out
```

При чтении сначала найдите интервал пользовательской задержки, а затем проверьте:

- сколько времени горутина была готова к выполнению;
- на каком канале, мьютексе, системном вызове или сетевой операции она ожидала;
- не совпало ли событие с паузой сборщика мусора;
- образовалась ли очередь из однотипных горутин;
- завершились ли дочерние горутины после отмены запроса.

Не записывайте длинную трассировку «на всякий случай»: файл быстро растёт, а нужный
интервал становится труднее найти.

## Пример сопоставления данных

Допустим, хвостовая задержка HTTP-запросов выросла, но процессор загружен только
наполовину. Проверка может выглядеть так:

1. Сравните `/sched/latencies:seconds` и число готовых G с обычным уровнем. Если они
   не выросли, нехватка процессорного времени маловероятна.
2. Сохраните два профиля горутин с интервалом. Повторяющиеся стеки ожидания одного
   пула соединений или внешнего вызова указывают на очередь вне планировщика.
3. Если в стеках преобладает ожидание мьютекса или канала, на короткое время снимите
   соответствующий профиль и найдите владельца задерживающего ресурса.
4. Запишите трассировку вокруг запроса. Проверьте, была ли его G готова, но не
   выполнялась, или всё время оставалась в ожидании внешнего события.
5. Измените одну предполагаемую причину и повторите измерение при той же нагрузке.

Если же одновременно растут загрузка процессора, число готовых G и задержка
планирования, исследуйте горячий вычислительный код, работу сборщика и длинные
участки, которые трудно вытеснить. Одна метрика без этого сопоставления причину не
доказывает.

## Регистратор полёта

`runtime/trace.FlightRecorder` хранит движущееся окно последних событий. Его можно
запустить заранее, а при редком скачке задержки сохранить уже произошедшие события.

```go
package diagnostics

import (
	"os"
	"runtime/trace"
	"time"
)

func StartRecorder() (*trace.FlightRecorder, error) {
	recorder := trace.NewFlightRecorder(trace.FlightRecorderConfig{
		MinAge:   10 * time.Second,
		MaxBytes: 32 << 20,
	})
	if err := recorder.Start(); err != nil {
		return nil, err
	}
	return recorder, nil
}

func SaveRecorder(recorder *trace.FlightRecorder, name string) error {
	file, err := os.Create(name)
	if err != nil {
		return err
	}
	if _, err := recorder.WriteTo(file); err != nil {
		_ = file.Close()
		return err
	}
	return file.Close()
}
```

После запуска вызовите `defer recorder.Stop()`. Одновременно может работать только
один регистратор полёта. `MaxBytes` — ориентир для размера окна, а не строгий предел
всех затрат памяти или размера результата `WriteTo`. Накладные расходы и подходящий
размер окна проверяйте на своей нагрузке.

## `schedtrace` для короткой проверки

Среда выполнения может периодически печатать своё состояние в стандартный поток
ошибок:

```bash
GODEBUG=schedtrace=1000,scheddetail=1 ./service
```

Такой вывод помогает быстро увидеть `GOMAXPROCS`, очереди готовых горутин и состояния
G, M и P. Формат относится к диагностике реализации, поэтому не стройте на нём
постоянный разборщик и не заменяйте им метрики приложения.

<a id="когда-менять-gomaxprocs"></a>

## Когда менять `GOMAXPROCS`

В проекте с версией языка Go 1.27 среда выполнения по умолчанию учитывает число
логических процессоров, привязку процесса к процессорам и квоту cgroup в Linux. Она
также может обновлять значение при изменении этих ограничений.

Переменная окружения `GOMAXPROCS` и вызов `runtime.GOMAXPROCS(n)` задают явное значение
и отключают автоматическое обновление. Вернуть поведение по умолчанию можно через
`runtime.SetDefaultGOMAXPROCS()`.

Не используйте `GOMAXPROCS` как ограничитель числа запросов, заданий или соединений.
Для этого нужны отдельные очереди, семафоры и пулы. Менять `GOMAXPROCS` стоит только
после измерения исходного состояния и повторной проверки пропускной способности,
хвостовой задержки и затрат процессора.

## Частые ошибки диагностики

- **Считать любую ожидающую горутину утечкой.** Ожидание сети или канала нормально;
  утечку показывает устойчивый рост и повторяющийся стек без пути завершения.
- **Искать ожидание в профиле процессора.** Он показывает выполнявшийся код, а не
  время, проведённое вне процессора.
- **Делать вывод по одному снимку.** Нужны базовый уровень, проблемный интервал и
  сопоставимая нагрузка.
- **Записывать слишком длинную трассировку.** Начните с нескольких секунд вокруг
  воспроизводимого события или используйте регистратор полёта.
- **Сразу увеличивать `GOMAXPROCS`.** Очередь может находиться в базе данных,
  блокировке или внешней службе и не зависеть от числа P.
- **Оставлять подробное профилирование включённым постоянно.** Сначала измерьте его
  влияние и выберите минимальную достаточную частоту выборки.

## Краткий порядок работы

1. Зафиксируйте симптом, нагрузку и исходную конфигурацию.
2. Сравните метрики процессора, горутин и задержки планирования с обычным уровнем.
3. Выберите один профиль по симптому, не включая все средства одновременно.
4. Запишите короткую трассировку, если важен порядок событий.
5. Сформулируйте одну проверяемую гипотезу и измените одну причину.
6. Повторите измерение при сопоставимой нагрузке.

## Краткий итог

- Начинайте с наблюдаемого симптома, а не с изменения `GOMAXPROCS`.
- Метрики, профили и трассировка отвечают на разные вопросы.
- Гипотезу подтверждают сопоставлением нескольких источников и повторным измерением.
