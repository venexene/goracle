# Выравнивание и компоновка структур в Go

> **Проверено:** Go 1.27 · **Уровень:** младший разработчик — углублённый

Размеры и смещения зависят от компилятора и целевой архитектуры. Не используйте
неявную компоновку структуры как внешний двоичный формат.

**Перед чтением:** [модель памяти](../memory.md), структуры и базовые типы.
**После главы:** вы сможете вычислить смещения полей, проверить их для выбранной
`GOARCH` и решить, оправдана ли перестановка полей.
[Задания и самопроверка](../../../practice.md#alignment).

## Зачем требуется выравнивание

**Выравнивание** задаёт допустимые адреса значения. Если выравнивание типа равно
четырём байтам, адрес значения должен быть кратен четырём. Размер и выравнивание
не обязаны совпадать: на `amd64` значение `complex128` занимает 16 байт, но
выровнено по границе 8 байт.

Компилятор сохраняет порядок полей структуры. Если очередное поле нельзя начать
сразу после предыдущего, между ними появляются неиспользуемые байты —
**отступ**. Завершающий отступ делает размер структуры кратным её выравниванию,
чтобы элементы массива таких структур тоже начинались с допустимых адресов.

Правильное выравнивание важно для корректности некоторых машинных и атомарных
операций. Уменьшение отступов может быть полезно, когда программа хранит миллионы
экземпляров структуры, но в обычном прикладном коде понятность полей важнее
экономии нескольких байтов.

## Размеры на `amd64`

Таблица относится к стандартному компилятору Go 1.27 для `amd64`:

| Тип | Размер, байт | Выравнивание, байт |
|---|---:|---:|
| `bool`, `byte`, `int8`, `uint8` | 1 | 1 |
| `int16`, `uint16` | 2 | 2 |
| `int32`, `uint32`, `float32`, `rune` | 4 | 4 |
| `int64`, `uint64`, `float64` | 8 | 8 |
| `complex64` | 8 | 4 |
| `complex128` | 16 | 8 |
| `int`, `uint`, `uintptr`, указатель, `map`, `chan`, функция | 8 | 8 |
| `string` | 16 | 8 |
| срез | 24 | 8 |
| интерфейс | 16 | 8 |

На 32-разрядной цели размеры указателей, `int` и составных заголовков меньше, а
выравнивание 64-разрядных чисел у стандартного компилятора может быть равно
четырём. Проверяйте целевую сборку, а не переносите таблицу механически.

## Три правила для структуры

1. Выравнивание структуры равно максимальному выравниванию её полей.
2. Смещение каждого поля кратно выравниванию типа этого поля.
3. Размер структуры кратен выравниванию самой структуры.

Рассмотрим два типа с одинаковыми данными:

```go
type Value struct {
    Enabled bool
    Count   int64
    Code    uint16
}

type CompactValue struct {
    Count   int64
    Code    uint16
    Enabled bool
}
```

На `amd64` первый тип занимает 24 байта:

| Смещение | Содержимое |
|---:|---|
| 0 | `Enabled` — 1 байт |
| 1–7 | отступ перед `Count` |
| 8–15 | `Count` |
| 16–17 | `Code` |
| 18–23 | завершающий отступ |

`CompactValue` занимает 16 байт: `Count` расположен на смещении 0, `Code` — на
8, `Enabled` — на 10, а оставшиеся пять байтов образуют завершающий отступ.
Группировка полей с большим выравниванием часто уменьшает размер, но это
эвристика, а не требование стиля.

## Как проверить компоновку

Пакет `unsafe` предоставляет три операции:

- `unsafe.Sizeof(x)` — размер значения вместе с отступами;
- `unsafe.Alignof(x)` — требуемое выравнивание;
- `unsafe.Offsetof(x.Field)` — смещение поля от начала структуры.

Полная запускаемая программа:

```go
package main

import (
    "fmt"
    "unsafe"
)

type Value struct {
    Enabled bool
    Count   int64
    Code    uint16
}

func main() {
    var value Value
    fmt.Printf("size=%d align=%d\n",
        unsafe.Sizeof(value), unsafe.Alignof(value))
    fmt.Printf("Enabled=%d Count=%d Code=%d\n",
        unsafe.Offsetof(value.Enabled),
        unsafe.Offsetof(value.Count),
        unsafe.Offsetof(value.Code))
}
```

Для `linux/amd64` программа выводит размер 24, выравнивание 8 и смещения
`0`, `8`, `16`. Это прямой программный способ проверки выбранной сборки, но не
обещание одинакового результата для всех архитектур и будущих компиляторов.

Проверяемая версия примера находится в
[`examples/runtimeinfo/layout.go`](https://github.com/venexene/goracle/blob/main/examples/runtimeinfo/layout.go),
а утверждения о размерах и выравнивании — в
[`layout_test.go`](https://github.com/venexene/goracle/blob/main/examples/runtimeinfo/layout_test.go).

### Проверка разных архитектур

Тестовый исполняемый файл можно собрать без запуска на текущем компьютере:

```bash
cd examples
GOARCH=386 go test -c -o /tmp/runtimeinfo-386.test ./runtimeinfo
GOARCH=arm64 go test -c -o /tmp/runtimeinfo-arm64.test ./runtimeinfo
```

Такая сборка обнаруживает непереносимые предположения в коде, но не печатает
смещения для другой архитектуры. Чтобы увидеть значения, запустите программу на
соответствующей машине или в подходящем эмуляторе.

## Вложенные структуры и массивы

Вложенный тип сохраняет собственный размер и выравнивание:

```go
type Inner struct {
    Number int64
    Flag   bool
}

type Outer struct {
    Tag   byte
    Value Inner
}
```

На `amd64` `Inner` занимает 16 байт. В `Outer` после `Tag` нужны семь байтов
отступа, затем размещается `Inner`; итоговый размер равен 24 байтам.

Элементы массива `[N]T` расположены с шагом `unsafe.Sizeof(T)`. Именно поэтому
размер структуры включает завершающий отступ: без него второй элемент мог бы
начаться по адресу, не подходящему его полям.

## Поля нулевого размера

`struct{}` и массив длины ноль имеют нулевой размер. Несколько значений нулевого
размера по правилам языка могут иметь одинаковый адрес.

У стандартного компилятора поле нулевого размера в конце структуры ненулевого
размера может увеличить её размер. Дополнительный завершающий отступ не позволяет
адресу такого поля оказаться сразу за памятью объекта и совпасть с адресом
следующего объекта. Точное число добавленных байтов зависит от компоновки:

```go
type Marker struct{}

type A struct {
    Marker Marker
    Value  byte
}

type B struct {
    Value  byte
    Marker Marker
}
```

Не используйте адрес нулевого поля как уникальный идентификатор и всегда
проверяйте `unsafe.Sizeof`, если порядок таких полей важен для размера.

## Атомарные значения

Для нового кода удобнее типизированные обёртки `atomic.Int64`, `atomic.Uint64`,
`atomic.Bool` и `atomic.Pointer[T]`: их внутренняя компоновка обеспечивает нужное
выравнивание. При использовании старых функций над обычным `int64` или `uint64`
на 32-разрядных ARM, x86 и MIPS ответственность за 64-разрядное выравнивание
лежит на вызывающем коде.

Не копируйте структуру после первого использования атомарного поля. Это
ограничение связано с состоянием атомарного значения, а не с экономией отступов.

## Ложное совместное использование строки кэша

Если разные ядра часто записывают в независимые поля, находящиеся в одной строке
кэша, протокол согласования кэшей может передавать эту строку между ядрами. Это
называется **ложным совместным использованием** (false sharing).

Иногда поля раздвигают явным массивом байтов, однако размер строки кэша и
эффективность такого решения зависят от процессора. Жёсткий отступ в 64 байта —
платформенное предположение, а не переносимое правило Go. Сначала подтвердите
проблему сравнительным тестом и профилем процессора, затем повторите измерение
после изменения.

## Когда поля не следует переставлять

Перестановка меняет не только размер. Сохраните исходный порядок, если:

- структура отражает внешний порядок полей или используется позиционными
  литералами в другом пакете;
- порядок важен для читаемости, проверки или отражения через `reflect`;
- код намеренно взаимодействует с ABI или `unsafe`;
- уменьшение не подтверждено количеством экземпляров и измерением;
- изменение разносит связанные данные по большему числу строк кэша;
- перестановка указательных полей ухудшает ожидаемую работу сборщика мусора.

Для сети и файлов используйте явное кодирование — например, `encoding/binary`,
JSON или Protocol Buffers. Запись сырых байтов структуры зависит от отступов,
порядка байтов и архитектуры.

Автоматическое исправление всего проекта анализатором `fieldalignment -fix` не
рекомендуется: выигрыш может оказаться мнимым, а новый порядок — хуже для смысла,
совместимости или сканирования указателей. При необходимости закрепите версию
анализатора, запускайте сначала только отчёт и проверяйте каждую структуру
отдельно.

## Практическая проверка

1. Найдите структуру с большим числом одновременно живущих экземпляров.
2. Зафиксируйте её размер, смещения и число экземпляров.
3. Сгруппируйте поля с одинаковым или большим выравниванием, не нарушая договоры.
4. Добавьте тест, который сравнивает размер до и после на целевой архитектуре.
5. Выполните сборку хотя бы для `amd64`, `386` и `arm64`.
6. Измерьте общую живую кучу и производительность, а не только `Sizeof` одного
   значения.

## Краткий итог

- Смещение каждого поля кратно его выравниванию, а размер структуры кратен
  максимальному выравниванию полей.
- На `amd64` у `complex64` размер 8 байт, но выравнивание 4 байта.
- Последнее поле нулевого размера способно увеличить размер структуры; оно не
  должно описываться как поле, адрес которого делит память со следующим объектом.
- Перестановка полей полезна только при большом числе экземпляров и измеримом
  выигрыше.
- Проверяйте компоновку через `unsafe` и сборки для целевых архитектур.
