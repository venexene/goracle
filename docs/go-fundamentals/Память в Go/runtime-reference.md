# Версионный справочник по памяти Go 1.27

> **Проверено:** Go 1.27.0 · **Уровень:** углублённый

Эта страница фиксирует внутренние детали стандартного компилятора и среды
выполнения Go 1.27.0. Они помогают читать исходный код и профили, но не являются
гарантиями спецификации языка. Учебное объяснение начинается в
[главе о памяти](memory.md).

**Перед чтением:** [аллокатор](allocator.md), [стеки горутин](stacks.md) и
[диагностика](diagnostics.md). **После главы:** вы сможете проверить числовое
утверждение по исходному коду нужной версии Go и не принять внутренний порог за
договор языка. [Задания и самопроверка](../../practice.md#memory).

## Числовые ориентиры Go 1.27.0

| Деталь | Значение | Где задано |
|---|---:|---|
| Страница аллокатора | 8 КБ | `runtime/pageAlloc` |
| Классы размера | 68, включая нулевой | `runtime/sizeclasses.go` |
| Классы спанов | 136: для каждого размера варианты со сканированием и без него | `runtime/mheap.go` |
| Верхняя граница обычного малого класса | 32 КБ | `runtime/malloc.go` |
| Предельный размер tiny-объекта | меньше 16 байт | `runtime/malloc.go` |
| Заголовок выделения (Malloc header) | 8 байт | `internal/runtime/gc/malloc.go` |
| Порог применения заголовка | `goarch.PtrSize * goarch.PtrBits` | `internal/runtime/gc/malloc.go` |
| Минимальный стек горутины | 2 КБ | `runtime/stack.go` |
| Максимальный стек на 64-разрядной цели | 1 ГЦБ | `runtime/proc.go` |
| Максимальный стек на 32-разрядной цели | 250 МБ | `runtime/proc.go` |
| Явное значение, обычно допускаемое компилятором на стеке | до 64 КБ | `cmd/compile/internal/gc/main.go` |
| Неявное значение, обычно допускаемое компилятором на стеке | до 16 КБ | `cmd/compile/internal/gc/main.go` |

Число классов и граница малого объекта связаны, но не дают универсального
правила вида «всё до 32 КБ проходит одним путём». Наличие указателей, размер,
текущий кэш P и новые специализированные пути влияют на выбранную функцию.

### Размер арены

Арена — крупный участок адресного пространства, по которому среда выполнения
группирует метаданные кучи. В Go 1.27.0 её размер зависит от цели:

| Цель | Размер арены |
|---|---:|
| Большинство 64-разрядных систем | 64 МБ |
| Windows, iOS и 32-разрядные системы | 4 МБ |
| WebAssembly | 512 КБ |

Это не размер одного системного запроса и не объём памяти, который сразу обязан
стать резидентным.

## Путь выделения объекта

Размещение значения в куче сначала определяет компилятор. Нельзя утверждать,
что любой возвращённый указатель, интерфейс или замыкание обязательно создаёт
объект в куче: анализ учитывает весь доступный граф времени жизни и результаты
встраивания функций. Проверяйте конкретный код:

```bash
go build -gcflags='all=-m=2' ./...
```

Если выделение нужно, в Go 1.27 возможны такие пути:

1. Для известных компилятору типов размером менее 80 байт могут быть вызваны
   специализированные функции `mallocgcSmall*`.
2. Общий путь проходит через `mallocgc`.
3. Объекты без указателей размером менее 16 байт могут объединяться в блоке
   tiny-аллокатора.
4. Малые объекты берутся из класса размера через локальный `mcache` текущего P.
5. При исчерпании локального спана `mcache` получает спан у `mcentral`, а затем
   при необходимости у `mheap`.
6. Крупные объекты получают отдельный спан нужного числа страниц.

Специализированный путь — оптимизация реализации, а не новая семантика языка:
объект остаётся обычным объектом кучи и учитывается сборщиком мусора.

## Спаны и метаданные указателей

`mspan` описывает непрерывный набор страниц одного класса. Для малых объектов
спан делится на одинаковые ячейки. Вариант `noscan` используется, когда объекты
не содержат указателей, которые должен обходить сборщик; вариант `scan` — когда
такие указатели возможны.

Для малых объектов метаданные указателей могут храниться в битовой карте спана.
Более крупное выделение получает заголовок размером 8 байт. Порог равен
`goarch.PtrSize * goarch.PtrBits`: 512 байт на 64-разрядной цели и 128 байт на
32-разрядной. Поэтому фиксированное число 512 нельзя переносить на все `GOARCH`.

Распределитель страниц `pageAlloc` использует иерархические сводки свободных
участков. Называть его обычным радиксным деревом неточно: это специализированная
многоуровневая структура над битовыми картами страниц.

## Освобождение и очистка страниц

Недостижимые объекты обнаруживает сборщик мусора. После очистки спана его ячейки
могут быть повторно использованы средой выполнения. Фоновый очиститель страниц
ищет достаточно свободные участки и вызывает внутренний `sysUnused`.

`sysUnused` платформозависимым способом сообщает ОС, что физическое содержимое
страниц больше не нужно. На Linux это обычно связано с `madvise`. Виртуальное
адресное пространство при этом может сохраниться, поэтому процесс способен
быстро использовать те же адреса снова.

Разницу видно в метриках:

- `/memory/classes/heap/free:bytes` — свободная память в спанах, ещё не
  возвращённая ОС;
- `/memory/classes/heap/released:bytes` — память свободных спанов, физические
  страницы которой возвращены ОС;
- `/memory/classes/heap/objects:bytes` — память объектов кучи.

## Стеки горутин

`stackMin` в Go 1.27 равен 2048 байтам, но это не означает, что каждая новая
горутина всегда получает ровно 2 КБ. Среда выполнения вычисляет
`startingStackSize` по среднему использованию стеков после сборок мусора и может
выбрать большее начальное значение.

Малые стеки переиспользуются через кэши и общие списки. Для больших стеков
`stackLarge` содержит массив списков; индекс соответствует двоичному логарифму
числа страниц. Это не один смешанный список блоков разного размера.

При нехватке места `newstack` выделяет больший непрерывный стек, `copystack`
переносит используемую часть и исправляет известные среде выполнения указатели.
Сборщик мусора может уменьшить малоиспользуемый стек. Подробности и диагностика
роста приведены в [отдельной главе](stacks.md).

## Пороги компилятора для значений на стеке

В обычной инициализации компилятора Go 1.27 устанавливаются два разных предела:

- `MaxStackVarSize = 64 * 1024` — для явных локальных переменных;
- `MaxImplicitStackVarSize = 16 * 1024` — для неявно создаваемых значений,
  например некоторых литералов и операций `new`.

Это входные данные анализа времени жизни, а не гарантия «значение меньше порога
всегда на стеке». Значение может уйти в кучу по времени жизни или исчезнуть после
оптимизации; слишком крупное значение также может быть размещено иначе ради
ограничения роста стека.

## Границы диагностических инструментов

| Инструмент | Показывает | Не показывает |
|---|---|---|
| профиль `heap` / `inuse_space` | выборку удерживаемых объектов кучи | RSS и каждое выделение без выборки |
| профиль `allocs` / `alloc_space` | выборку накопленных выделений | только живые объекты |
| `runtime/metrics` | числовые показатели среды выполнения | строки кода, создавшие объекты |
| `runtime.MemStats` | сводный снимок памяти Go | точную память процесса |
| `GODEBUG=gctrace=1` | циклы и размеры кучи вокруг сборки мусора | места выделения |
| трассировка выполнения | события планировщика, сборщика и изменение кучи | обычный профиль всех мест выделения |
| RSS и cgroup | память с точки зрения ОС или контейнера | владельца каждого объекта Go |

Профили памяти зависят от `runtime.MemProfileRate`; профиль кучи может быть не
новее последней завершённой сборки мусора. Подробный порядок работы описан в
[главе о диагностике](diagnostics.md).

## Как проверять детали другой версии

1. Зафиксируйте точную версию командой `go version`.
2. Откройте исходный код соответствующего тега, а не ветку `master`.
3. Ищите имя константы или функции, а не только числовое значение.
4. Проверьте платформенные файлы с суффиксами `_linux`, `_windows`, `_arm64` и
   условия сборки.
5. Отделите наблюдаемое внутреннее поведение от гарантий спецификации и
   документированных пакетов.
6. Подтвердите практический вывод тестом или профилем на своей целевой системе.

## Краткий итог

- Внутренние числовые пороги относятся к Go 1.27.0 и конкретной целевой
  архитектуре, если не сказано обратное.
- Не каждое выделение в Go 1.27 проходит через один и тот же вызов `mallocgc`.
- Возврат физических страниц через `sysUnused` не обязан удалять виртуальное
  отображение.
- Пороги компилятора не заменяют анализ времени жизни.
- Для прикладной диагностики начинайте с метрик и профилей, а к исходному коду
  среды выполнения переходите только ради конкретной гипотезы.
