# Диагностика памяти в Go

> **Проверено:** Go 1.27 · **Уровень:** младший разработчик — углублённый

**Перед чтением:** [модель памяти](memory.md) и базовое умение запускать тесты.
**После главы:** вы сможете отличить рост живой кучи от высокого темпа выделений,
утечки горутин и роста памяти процесса, снять подходящий профиль и проверить
гипотезу повторным измерением. [Задания и самопроверка](../../practice.md#memory).

## Сначала определите, что именно растёт

Слово «память» может означать разные величины. Один граф процесса не доказывает
утечку объектов Go.

| Наблюдение | Что измерить | Следующий инструмент |
|---|---|---|
| После сборок мусора растёт живая куча | `/gc/heap/live:bytes` | профиль `heap`, показатель `inuse_space` |
| Живая куча стабильна, но сборки частые | `/gc/heap/allocs:bytes` и число сборок | профиль `allocs`, показатель `alloc_space` |
| Растёт число горутин | `/sched/goroutines:goroutines` | профили `goroutine` и `goroutineleak` |
| Растут стеки | `/memory/classes/heap/stacks:bytes` | профиль горутин и трассировка выполнения |
| Растёт RSS, а куча Go стабильна | RSS, память cgroup, отображения процесса | средства ОС, затем cgo и отображённые файлы |

Сравнивайте показатели при одинаковой нагрузке и после прогрева. Разовый пик во
время компиляции шаблона, заполнения кэша или очередной сборки мусора не равен
постоянному росту.

## Метрики среды выполнения

Для автоматического наблюдения предпочтителен пакет `runtime/metrics`: у его
метрик устойчивые имена и явно указанные единицы измерения. Полный запускаемый
пример находится в [описании `examples/runtimeinfo`](https://github.com/venexene/goracle/tree/main/examples#проверяемые-сценарии-памяти).

```go
samples := []metrics.Sample{
    {Name: "/gc/heap/live:bytes"},
    {Name: "/gc/heap/allocs:bytes"},
    {Name: "/memory/classes/heap/stacks:bytes"},
    {Name: "/sched/goroutines:goroutines"},
}
metrics.Read(samples)

for _, sample := range samples {
    fmt.Printf("%s = %d\n", sample.Name, sample.Value.Uint64())
}
```

Перед чтением значения в библиотечном коде полезно сверять его вид с
`metrics.All()`: набор метрик расширяется между выпусками Go. Не складывайте
метрики разных единиц, даже если обе представлены числом.

### Когда нужен `runtime.MemStats`

`runtime.ReadMemStats` остаётся полезным для существующего кода и разовых
снимков. Основные поля следует читать так:

| Поле | Смысл | Чего оно не показывает |
|---|---|---|
| `HeapAlloc` | байты занятых объектов кучи Go | всю память процесса |
| `TotalAlloc` | накопленный объём выделений с запуска | текущую живую кучу |
| `HeapSys` | виртуальное пространство, полученное средой выполнения для кучи | точный RSS |
| `HeapIdle` | часть спанов кучи без занятых объектов | объём уже возвращённых ОС страниц |
| `HeapReleased` | часть `HeapIdle`, физические страницы которой возвращены ОС | удалённое виртуальное отображение |
| `StackInuse` | память стеков горутин в используемых спанах | системные стеки потоков ОС |
| `Sys` | приближённый общий объём памяти, полученной средой выполнения | точную память процесса или контейнера |

Чтение статистики само по себе не объясняет, какой участок программы удерживает
объекты. Для этого нужен профиль.

## Профиль памяти в тесте производительности

Сначала измерьте число операций и байт выделений:

```bash
cd examples
go test -run='^$' -bench=BenchmarkRetainedBlocks -benchmem ./runtimeinfo
```

Затем сохраните профиль:

```bash
go test -run='^$' -bench=BenchmarkRetainedBlocks \
  -memprofile=before.pprof ./runtimeinfo
go tool pprof -sample_index=inuse_space before.pprof
```

В интерактивном режиме начните с `top`, затем используйте `list ИмяФункции` и
`web`, если в системе установлен Graphviz. Для поиска высокого темпа временных
выделений смените показатель:

```bash
go tool pprof -sample_index=alloc_space before.pprof
```

- `inuse_space` показывает объём объектов из выборки, которые оставались живы;
- `alloc_space` показывает накопленный объём выделений из выборки независимо от
  того, были ли объекты позднее освобождены.

Профили памяти **выборочные**. Частота задаётся `runtime.MemProfileRate`; по
умолчанию профилируется примерно одно выделение на 512 КиБ выделенной памяти.
Профиль кучи также может отражать состояние не новее последней завершённой
сборки мусора. Поэтому небольшие значения не стоит трактовать как точный список
каждого объекта.

После изменения кода снимите профиль при той же нагрузке и сравните его с
исходным:

```bash
go test -run='^$' -bench=BenchmarkRetainedBlocks \
  -memprofile=after.pprof ./runtimeinfo
go tool pprof -base=before.pprof -sample_index=inuse_space after.pprof
```

Отрицательное значение в разностном профиле означает уменьшение относительно
базы, а не «отрицательную память».

## Профили работающей службы

Пакет `net/http/pprof` регистрирует диагностические обработчики. Не публикуйте
их на внешнем интерфейсе без отдельной аутентификации и сетевых ограничений:
профили раскрывают внутреннее устройство программы и создают дополнительную
нагрузку. Простейший безопасный вариант для разработки — отдельный сервер на
петлевом адресе:

```go
package main

import (
    "log"
    "net/http"
    _ "net/http/pprof"
)

func main() {
    go func() {
        log.Println(http.ListenAndServe("127.0.0.1:6060", nil))
    }()

    select {}
}
```

Снимок живой кучи можно открыть напрямую:

```bash
go tool pprof -sample_index=inuse_space \
  http://127.0.0.1:6060/debug/pprof/heap
```

Для накопленных выделений используйте `/debug/pprof/allocs`. Профиль
`goroutine` показывает все стеки, а появившийся в Go 1.27 профиль
`goroutineleak` оставляет только горутины, которые среда выполнения считает
заблокированными навсегда:

```bash
curl -o goroutineleak.pb.gz \
  http://127.0.0.1:6060/debug/pprof/goroutineleak
go tool pprof goroutineleak.pb.gz
```

Пустой `goroutineleak` не доказывает отсутствие прикладной утечки: горутина,
которая периодически просыпается или ждёт внешнее событие, может бесконечно
удерживать ссылки, но не соответствовать критерию профиля.

## Если растёт только память процесса

На Linux сопоставьте данные среды выполнения с показателями ОС:

```bash
ps -o pid,rss,vsz,cmd -p PID
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.max
```

В cgroup v1 пути отличаются. Значение `max` в `memory.max` означает отсутствие
заданного ограничения. RSS и `memory.current` могут включать системные стеки,
cgo, отображённые файлы, разделяемую память и страницы, которые среда выполнения
пока не вернула ОС.

Если живая куча Go стабильна, проверьте:

1. растёт ли число потоков и горутин;
2. использует ли программа cgo или библиотеку на C;
3. создаются ли отображения через `mmap`;
4. закрываются ли тела HTTP-ответов, файлы, строки базы данных и таймеры;
5. не объясняется ли разница кэшем файловых страниц.

Ограничение `GOMEMLIMIT` и функция `debug.SetMemoryLimit` управляют целью для
памяти среды выполнения Go, но не являются жёстким пределом RSS всего процесса.

## Сборщик мусора и трассировка

`GODEBUG=gctrace=1` помогает увидеть частоту сборок, размер кучи до и после
маркировки и долю процессорного времени сборщика. Он полезен для проверки
гипотезы о слишком высоком темпе выделений, но не указывает строки кода.

Трассировка выполнения показывает планирование горутин, паузы сборщика и
изменение размера кучи:

```bash
go test -run TestMemoryMetricsAreAvailable -trace=trace.out ./runtimeinfo
go tool trace trace.out
```

Обычная трассировка не заменяет профиль мест выделения. Подробные события
выделения и освобождения доступны через экспериментальный режим
`GODEBUG=traceallocfree=1`, который заметно увеличивает объём трассировки и накладные
расходы; для первого исследования используйте профиль памяти.

## Проверяемая последовательность

1. Зафиксируйте версию программы, нагрузку, длительность и ограничение памяти.
2. Определите растущую величину: живая куча, накопленные выделения, стеки,
   горутины или только память процесса.
3. Снимите профиль, соответствующий этой величине.
4. Сформулируйте одну гипотезу по верхним строкам профиля.
5. Измените одну причину: ограничьте кэш, переиспользуйте буфер, завершите
   горутину или закройте ресурс.
6. Повторите тот же замер и сравните профили.
7. Проверьте задержки и корректность: уменьшение выделений не должно ухудшить
   поведение программы.

Без последнего повторного измерения изменение остаётся предположением.

## Краткий итог

- Сначала определяйте растущую величину, затем выбирайте профиль.
- `inuse_space` отвечает на вопрос об удерживаемой куче, `alloc_space` — о темпе
  выделений; оба показателя основаны на выборке.
- RSS нельзя вывести из одного поля `runtime.MemStats`.
- Утечка горутин может удерживать и стеки, и объекты кучи.
- Исправление считается подтверждённым только после повторного замера при той же
  нагрузке.
